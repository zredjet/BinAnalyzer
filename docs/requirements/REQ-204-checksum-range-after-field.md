## 背景・動機

チェックサムの範囲（`range` / `ranges` の式、`fields` の名前）は、チェックサムのフィールドを読んだ直後に評価する。そのため、範囲の大きさ・位置がチェックサムの欄より**後ろのフィールド**で決まる形式を、そのままでは書けない。

REQ-199 では、後ろのフィールドを `seek` + `seek_restore` で先に読む作業用のフィールド（`padding: true`）を置いて避けた。

| 定義 | チェックサム | 範囲を決める後ろのフィールド | 回避策 |
|---|---|---|---|
| ogg | ページの CRC（22 バイト目） | セグメント表（ページの大きさ） | `peek_num_segments`・`peek_segment_table` |
| otf | 表のレコードの checksum | offset・length | `peek_offset`・`peek_length` |

先読みのフィールドは同じ値を 2 度読み、JSON・ゴールデンにも出る。ほかにも次の形が同じ制約を持つ。

- MKV の CRC-32 要素（親の要素の、この要素より**後ろの子すべて**に対する値。formats/mkv.bdef.yaml では検証していない）
- ZIP のローカルファイルヘッダの CRC-32（後ろのデータに対する値。展開も要るので REQ-207 と組み合わせる）

## 機能要件

### 追加する機能

- [ ] **チェックサムの検証を、チェックサムのフィールドを含む struct を読み終えた後に行う指定**（例: `checksum:` の `verify: after_struct`。自動で遅らせるか、指定させるかは設計で決める）。そのとき範囲の式は struct の終わりの変数で評価し、`fields` は後ろの兄弟も引ける
- [ ] 範囲を「このフィールドより後ろの兄弟すべて」「親の struct の残り」のように書く手段を設計で決める（MKV の CRC-32 要素）

### 変更する既存機能

- [ ] formats/ogg.bdef.yaml・formats/otf.bdef.yaml の先読みのフィールドを外し、後ろのフィールドで範囲を書く（検証の結果は変えない）
- [ ] formats/mkv.bdef.yaml の CRC-32 要素を検証する（入れられるなら）

### 変更しないもの（スコープ外）

- 展開した中身に対するチェックサム（REQ-207）
- 今のチェックサム（フィールドを読んだ直後に評価する）の意味。指定しない限り変えない

## 受入条件

1. [ ] ogg のページの CRC が、先読みのフィールド無しで今と同じ結果（ffmpeg の出力で ✓、1 バイト書き換えで ✗）になること
2. [ ] otf の表のチェックサムが、先読みのフィールド無しで今と同じ結果になること（fontTools の判定と一致）
3. [ ] 遅らせたチェックサムでも、patch・GUI の編集のチェックサムの再計算が今と同じく動くこと（`ChecksumCoverage` が正しいこと）
4. [ ] MKV の CRC-32 要素を検証する場合は、mkvmerge などが書いたファイルで ✓ になること
5. [ ] ゴールデンの差分が、先読みのフィールドが消えることだけであること
6. [ ] 既存テストが全て通過すること（`dotnet test` 全通過）

## 設計メモ

### 設計方針（案）

- struct の子を読み終えた時点で、遅らせたチェックサムのフィールドを検証し、子の一覧のノードを検証の結果を持つノードに差し替える
- 範囲の式の中の `_offset` の意味（チェックサムのフィールドの直後か、struct の終わりか）が変わるので、遅らせるときは struct の先頭からの位置を表す変数か、フィールドの位置を表す変数（例: `_field_offset`）を用意する

### 懸念事項

- 繰り返しの要素・switch の中など、struct の終わりが複数の階層にある場合のタイミング
- エラー継続モードで、struct の途中でエラーになったときに遅らせた検証をどうするか
