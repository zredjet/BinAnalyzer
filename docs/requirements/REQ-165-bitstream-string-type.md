## 背景・動機

> **見直し（2026-09-24）**: 課題は今もある（`YamlToIrMapper.IsAllowedInBitstreamStruct` は整数型・`virtual`・`switch`・`struct` のみを許可）。ただし当初の型名 `string` / `string0` は今の DSL に無いので、固定長の文字列型（`ascii` / `utf8` / `sjis` / `latin1` / `utf16le` / `utf16be`）と NULL 終端の文字列型（`asciiz` / `utf8z`）に読み替えて機能要件・受入条件を直した。

現在のビットストリームモード（`mode: bitstream`）では、整数型（`uint8`, `uint16`, `uint32`, `uint64`）、`virtual`、`switch`、`struct` のみが許可されている。文字列型（`ascii` / `utf8` / `asciiz` など）はビットストリーム内では使用不可。

一部のプロトコル（例: Bluetooth の広告パケット）ではビットフィールドと文字列フィールドが混在する。バイト境界にアラインされた文字列であれば、ビットストリームモード内でもデコード可能であるべき。

## 機能要件

### 追加する機能

- [ ] ビットストリームモードでの固定長文字列型（`ascii` / `utf8` / `sjis` / `latin1` / `utf16le` / `utf16be`）のサポート（バイト境界アライン必須）
- [ ] ビットストリームモードでの NULL 終端文字列型（`asciiz` / `utf8z`）のサポート
- [ ] バイト境界にアラインされていない場合のバリデーションエラー

### 変更する既存機能

- [ ] `YamlToIrMapper` — ビットストリーム構造体のフィールド型チェック緩和
- [ ] `BinaryDecoder` — ビットストリーム内文字列フィールドのデコード処理追加
- [ ] `BitReader` — バイト境界アライン確認メソッド追加

### 変更しないもの（スコープ外）

- ビットアラインされていない文字列（ビット単位の文字列は非サポート）
- `bytes` 型のビットストリームサポート

## 受入条件

1. [ ] ビットストリーム内で固定長文字列型がデコードできること（バイト境界アライン時）
2. [ ] ビットストリーム内で NULL 終端文字列型がデコードできること（バイト境界アライン時）
3. [ ] バイト境界にアラインされていない位置で文字列型を使用した場合にエラーが発生すること
4. [ ] 文字列フィールドの前後にビットフィールドが正しくデコードされること
5. [ ] 既存テストが全て通過すること（`dotnet test` 全通過）
