## 背景・動機

圧縮データの型（`deflate`・`zlib`・`gzip` など）は中身を展開して表示する。展開したバイト列は、中身を struct で分解しないときだけ持つ（`DecodedCompressed.RawDecompressed`。分解したときは null）。チェックサムの範囲は元のデータの中しか指せないので、**展開した中身**に対するチェックサムは検証していない。

| 定義 | チェックサム | 位置 |
|---|---|---|
| gzip | 展開後のデータの CRC-32（と ISIZE = 展開後のバイト数 mod 2^32） | 中身の後ろ |
| zip | ローカルファイルヘッダ・データ記述子・中央ディレクトリの CRC-32 | ヘッダは中身の前、データ記述子は後ろ、中央ディレクトリは別の場所 |
| lz4 | Content Checksum（展開後の全データの xxHash-32） | 中身の後ろ。ただし lz4.bdef.yaml はブロックを展開していない |

gzip と ZIP の CRC-32 は、アーカイブが壊れていないかを確かめる最も基本的な情報。

## 機能要件

### 追加する機能

- [ ] **チェックサムの入力に、圧縮データのフィールドの展開した中身を指定する**（例: `checksum:` の `decompressed: compressed_data`。形は設計で決める）。展開に失敗したときは検証しない
- [ ] 展開後のバイト数（ISIZE）を式で参照する手段を設計で決める（`validate:` で比べられるように）

### 変更する既存機能

- [ ] formats/gzip.bdef.yaml の CRC-32 と ISIZE を検証する
- [ ] formats/zip.bdef.yaml の CRC-32 を検証する（格納・Deflate のエントリ。ローカルファイルヘッダの CRC-32 は REQ-204 の後ろのフィールドの指定と組み合わせる）

### 変更しないもの（スコープ外）

- lz4 のブロックの展開（LZ4 のブロック形式。lz4.bdef.yaml はフレームを分解する定義で、エンジンの `lz4` 型は使っていない）
- 暗号化された ZIP のエントリ

## 受入条件

1. [ ] `gzip` の出力の CRC-32 と ISIZE が ✓ / 検証成功、中身を 1 バイト書き換えると ✗ になること
2. [ ] `zip`（Info-ZIP）と macOS の `ditto -c -k` の出力の、格納・Deflate のエントリの CRC-32 が ✓ になること
3. [ ] 展開に失敗したエントリ（エラー継続モード）では検証しない（✓ も ✗ も出ない）こと
4. [ ] patch・GUI の編集のチェックサムの再計算で、展開した中身に対するチェックサムを書き換えない（元のデータを変えても再圧縮はしない）ことが示されること
5. [ ] 既存テストが全て通過すること（`dotnet test` 全通過）

## 設計メモ

### 設計方針（案）

- 兄弟の圧縮データのフィールド（`DecodedCompressed`）の展開したバイト列を入力にする。今は struct で分解すると捨てているので、チェックサムに使うときは残す。ZIP のように中身が入れ子の struct の中にある場合の参照の書き方（メンバーアクセス）を決める

### 懸念事項

- 展開したバイト列を常に持つとメモリを使う（REQ-180 のノードの大きさ）。チェックサムに使う場合だけ持つ
