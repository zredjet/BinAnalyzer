## 背景・動機

現在のテストはユニットテストと統合テストが中心で、実際のバイナリファイルのデコード結果全体の正当性を検証する仕組みがない。エンジンや DSL の変更時にデコード結果が意図せず変わるリグレッションを防止するため、ゴールデンファイル（期待値ファイル）ベースのテストフレームワークが必要。

### ユースケース

- エンジン変更後に全フォーマットのデコード結果が変わっていないことを確認
- 新規フォーマット定義の期待値を記録し、以降の変更で壊れないことを保証
- `dotnet test` でゴールデンファイルテストも自動実行

## 機能要件

### 追加する機能

- サンプルバイナリファイル + `.bdef.yaml` + 期待値ファイル（JSON or テキスト）の3点セットでテストケースを構成
- デコード結果を期待値ファイルと比較し、差分があればテスト失敗
- 期待値ファイルの更新コマンド（`--update-golden` 的な仕組み）
- フォーマットごとにテストケースディレクトリを配置

### 変更しないもの（スコープ外）

- バイナリファイルの自動生成
- パフォーマンスリグレッション検出（ベンチマークは別）
- 出力フォーマット（JSON, tree等）ごとのゴールデンファイル（JSON形式のみ）

## 受入条件

1. サンプルバイナリ + フォーマット定義 + 期待値ファイルの3点セットでテストが実行されること
2. デコード結果と期待値が一致する場合にテスト成功となること
3. デコード結果と期待値に差分がある場合にテスト失敗となり、差分が表示されること
4. 期待値ファイルの更新メカニズムが存在すること
5. `dotnet test` で自動実行されること
6. 最低 5 フォーマット分のゴールデンファイルが初期セットとして含まれること

## 実装

### 実装概要

- `tests/BinAnalyzer.Integration.Tests/GoldenFileTests.cs` — 30 フォーマットのゴールデンファイルテスト
- `testdata/golden/*.json` — 30 個のゴールデンファイル（JsonOutputFormatter の出力）
- 環境変数 `UPDATE_GOLDEN=1` でゴールデンファイルを再生成可能

### 使い方

```bash
# ゴールデンファイル生成・更新
UPDATE_GOLDEN=1 dotnet test --filter "FullyQualifiedName~GoldenFileTests"

# リグレッションテスト（通常実行）
dotnet test
```
