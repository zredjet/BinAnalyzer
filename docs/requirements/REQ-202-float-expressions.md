## 背景・動機

`float16` / `float32` / `float64` のフィールドの値は、式の中では double の変数になる。そのまま参照（`{scale}`）はできるが、式の整数の演算がすべて long への変換（`ConvertToLong`）を通すため、次のようになる（REQ-200 の実装で確かめた）。

- `<`・`<=`・`>`・`>=`・算術・ビット演算: デコード時に「Cannot convert Double ('1.5') to integer」のデコードエラー
- `==` / `!=`: long への変換に失敗すると `Equals` で比べるので、`{x == 1}` は x が 1.0 でも偽（double と long は等しくない）
- 浮動小数点数のリテラルが無い（`1.5` の `.` はメンバーアクセスとして読まれる）

検証（FormatValidator）はこれらを見つけないので、定義を書いたときは気付かず、その式を通るファイルで初めてエラーになる。浮動小数点数の値の範囲の `validate:`（サンプリング周波数が正、正規化された値が 0〜1 など）や、浮動小数点数の値による分岐（`switch_on`・`if:`）が書けない。

## 機能要件

### 追加する機能

- [ ] **比較演算子（`==`・`!=`・`<`・`<=`・`>`・`>=`）で、片方が浮動小数点数なら double として比べる**（整数と浮動小数点数の比較を含む。NaN との比較は偽、`!=` は真）
- [ ] 算術（`+`・`-`・`*`・`/`）で、片方が浮動小数点数なら double の結果にするか、エラーのままにするかを設計で決める（`%`・ビット演算・シフトは整数だけのまま）
- [ ] 浮動小数点数のリテラル（`1.5`・`1e-3` など）を足すかを設計で決める（`.` のメンバーアクセスとの区別）
- [ ] 整数への変換の関数（`int(x)` の切り捨てなど）を足すかを設計で決める

### 変更する既存機能

- [ ] 浮動小数点数に使えない演算（決めた方針で残るもの）を、検証で警告するか、デコードエラーの文言で型を示す

### 変更しないもの（スコープ外）

- 符号なし 64 ビットの整数の演算（REQ-201 で式は符号付きのままとした）
- 文字列と数値の暗黙の変換

## 受入条件

1. [ ] `float32` のフィールドで `validate: "{rate > 0}"` が、正の値で成功・0 以下で失敗すること
2. [ ] `{x == 1}` が x = 1.0 の float で真になること
3. [ ] NaN との比較の結果が IEEE 754 のとおりであること
4. [ ] 決めた方針の算術・リテラル・変換関数が動くこと（または使えないことが DSL リファレンスに書かれ、検証かエラーの文言で分かること）
5. [ ] 整数だけの式の結果が変わらないこと（ゴールデンが変わらない）
6. [ ] 既存テストが全て通過すること（`dotnet test` 全通過）

## 設計メモ

### 設計方針（案）

- 比較は「両方が整数なら long、どちらかが double なら double」の規則にする（C# の数値の昇格と同じ）
- 算術も同じ規則で double にできるが、`size:` などの整数を期待する場所に double が渡ったときの扱い（エラーにする・切り捨てる）を決める必要がある

### 懸念事項

- 式の値の型の規則は REQ-201 で見送った「符号なし 64 ビットの演算」とも関わる。まとめて規則を決めるか
