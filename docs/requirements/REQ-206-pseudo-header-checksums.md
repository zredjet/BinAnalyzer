## 背景・動機

REQ-199 で pcap の IPv4 のヘッダと ICMP のチェックサムを検証するようにしたが、TCP・UDP・ICMPv6 のチェックサムは**擬似ヘッダ**を含むので検証していない（formats/pcap.bdef.yaml の「対応していないもの」）。擬似ヘッダは連続したバイト列でなく、一部は計算した値なので、範囲（`range` / `ranges`）だけでは表せない。

| 上位 | 擬似ヘッダ |
|---|---|
| IPv4 の TCP・UDP（RFC 9293・768） | 送信元のアドレス（4）・宛先のアドレス（4）・0（1）・プロトコル番号（1）・TCP / UDP の長さ（2） |
| IPv6 の TCP・UDP・ICMPv6（RFC 8200 8.1 節） | 送信元のアドレス（16）・宛先のアドレス（16）・上位の長さ（4）・0（3）・次のヘッダ（1） |

アドレスは IP のヘッダのバイト列（外側の struct の範囲）、プロトコル番号・長さは式の値（IPv6 の拡張ヘッダがあれば次のヘッダは最後の拡張ヘッダの値、長さは拡張ヘッダを除いた値）。

## 機能要件

### 追加する機能

- [ ] **チェックサムの入力に、式の値を決まったバイト数のビッグエンディアンのバイト列として足す指定**（例: `append: [{value: "{protocol}", size: 2}, {value: "{tcp_length}", size: 2}]`。形は設計で決める）。範囲（外側の struct の IP アドレス）と並べて使う
- [ ] 入力の順序（擬似ヘッダ → TCP / UDP のヘッダとデータ）を指定どおりにつなぐ

### 変更する既存機能

- [ ] formats/pcap.bdef.yaml の TCP・UDP（IPv4 / IPv6）・ICMPv6 のチェックサムを検証する。IPv4 の UDP のチェックサム 0（「チェックサム無し」）は検証しない

### 変更しないもの（スコープ外）

- IP のフラグメントの再組み立て（2 つ目以降のフラグメントの TCP / UDP は分解していない）
- IPv6 のルーティングヘッダの最終の宛先（擬似ヘッダの宛先はルーティングヘッダの最後のアドレス）。見つけたら ✗ にならないよう検証しないか、別の要望とする

## 受入条件

1. [ ] tcpdump 4.99 の `-vvv` が「correct」とする TCP・UDP・ICMPv6 のチェックサムが ✓、「incorrect」とするものが ✗ になること（IPv4 と IPv6、拡張ヘッダ付きを含む）
2. [ ] IPv4 の UDP のチェックサム 0 は検証しない（✓ も ✗ も出ない）こと
3. [ ] スナップ長で切れたパケットは、デコードエラーでなく ✗ か検証しないこと
4. [ ] 既存テストが全て通過すること（`dotnet test` 全通過）

## 設計メモ

### 設計方針（案）

- IP のヘッダの先頭の位置を、IPv4 / IPv6 の struct で `_offset` から作業用の値に取っておき、アドレスの範囲はそこからの位置で書く（REQ-199 と同じ方法）

### 懸念事項

- 送信元のホストでキャプチャしたパケットは、チェックサムの計算を NIC に任せる（オフロード）ため TCP / UDP のチェックサムが誤った値のことが多い（tcpdump も「incorrect」と出す）。実際のキャプチャで ✗ が多く出ることを説明に書く
